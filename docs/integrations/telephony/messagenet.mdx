## Overview

[MessageNet](https://www.messagenet.it/) is an Italian VoIP provider offering SIP trunking. Dograh AI integrates with MessageNet by registering against your SIP trunk and bridging audio through a SIP/media gateway (typically Asterisk) running alongside your Dograh deployment.

Because MessageNet does not expose a REST call-control API, all signalling and media go over SIP/RTP. The configuration in Dograh stores the SIP URI and password for the trunk; the SIP/media gateway component is provisioned separately at deployment time.

## Prerequisites

Before setting up the MessageNet integration, you'll need:

- An active **MessageNet** account with at least one SIP trunk enabled
- The trunk's **SIP URI** (in the form `sip:5000000@sip.messagenet.it`)
- The trunk's **SIP password** (also called *user password* in the MessageNet portal)
- *(Optional)* One or more caller IDs / DIDs you've assigned to the trunk
- A SIP/media gateway (e.g. Asterisk + PJSIP) reachable from your Dograh backend — this is the component that actually speaks SIP to MessageNet and exposes a WebSocket audio leg to Dograh
- Dograh AI instance running and accessible

<Note>
The MessageNet portal exposes the SIP URI and user password under your trunk's account page (often labelled "SIP URI" / "Internal URI" and "SIP password"). Keep the password handy — it's the same one you'd give a softphone or any other SIP client.
</Note>

## SIP/Media Gateway

MessageNet, like other pure SIP trunks, requires a SIP-speaking component on your side to register the trunk and bridge audio. Dograh treats this component as an abstraction (`MessagenetSipGatewayClient`) so the same provider code works regardless of which backend you wire in.

The default ship state of the provider returns **HTTP 503 — "MessageNet SIP gateway is not configured"** for every outbound attempt. This is intentional: until you wire a real gateway, calls fail safely instead of half-working.

To make the integration live, point Dograh's gateway implementation at an Asterisk (or Kamailio, or other SIP-capable) instance configured with:

- A PJSIP endpoint/auth/registration for your MessageNet trunk
- A dialplan rule that routes outbound calls onto that endpoint
- An external-media / WebSocket bridge for the audio leg back to Dograh

This is the same pattern documented for [Asterisk ARI](./asterisk-ari.mdx) — in fact, an existing ARI deployment can usually be reused as the MessageNet gateway by adding a PJSIP endpoint pointed at MessageNet.

## Configuration in Dograh

### Step 1: Navigate to Telephony Settings

1. Open **/telephony-configurations** and click **Add configuration**
2. Select **MessageNet** as your provider

### Step 2: Enter Your MessageNet Credentials

| Field | Description | Example |
|-------|-------------|---------|
| **SIP URI** | The MessageNet trunk SIP URI | `sip:5000000@sip.messagenet.it` |
| **SIP Username** | *Optional.* SIP auth username — defaults to the user part of the SIP URI if you leave this blank. | `5000000` |
| **SIP Password** | The trunk's SIP password. Masked on read; resubmitting the masked value keeps the stored secret. | *(your password)* |
| **Caller IDs** | *Optional.* Comma- or array-style list of phone numbers / DIDs allowed as the outbound caller ID. | `+390212345678` |

Click **Save Configuration**.

### Step 3: Verify

If your SIP/media gateway is wired in, you can now place a test call from the Dograh UI. If not, you'll receive a clear 503 error pointing at the gateway component — that's the expected behaviour until the gateway is configured.

## Outbound Calls

1. Navigate to a workflow → **Test Call**
2. Pick a destination number (E.164 format)
3. The outbound caller ID is selected from the configured **Caller IDs** list on the trunk (or chosen explicitly per-call via the API)
4. The gateway dials the destination via the registered MessageNet trunk and streams audio back to Dograh over the configured WebSocket bridge

## Inbound Calls

Inbound MessageNet calls are routed to Dograh by the SIP/media gateway, not by an HTTP webhook. Configure your gateway's dialplan to route the dialled extension/DID into the Dograh-facing WebSocket bridge (see the [Asterisk ARI](./asterisk-ari.mdx) integration guide for a reference dialplan).

Dograh matches inbound calls to a workflow using the **called number** — there's no account-id concept on MessageNet trunks, so you can run multiple MessageNet trunks in the same organization as long as their caller IDs / DIDs don't overlap.

## Local development with the bundled Asterisk gateway

The repo ships a ready-to-run Asterisk container under `asterisk/` and a `messagenet` docker-compose profile so you can exercise the full SIP path locally against a real MessageNet trunk.

### Prerequisites

- Docker + docker compose installed
- A real MessageNet trunk you can register against (SIP URI + password)
- The Dograh stack already running (`docker compose up`)
- A public port-forward for `5060/udp` on your machine — only required if you want to receive **inbound** calls; outbound-only testing works behind NAT since the registration keeps the SIP pinhole open

### Step 1: Fill in environment variables

In `api/.env`, set:

```bash
MESSAGENET_GATEWAY_BACKEND=asterisk-ari
ARI_BASE_URL=http://asterisk:8088
ARI_APP_NAME=dograh-messagenet
ARI_USER=dograh
ARI_PASSWORD=<pick-any-strong-string>
MESSAGENET_PJSIP_ENDPOINT=messagenet
# Trunk credentials — used by the asterisk entrypoint to render conf.d/messagenet_local.conf
MESSAGENET_USER=<the user part of your SIP URI>
MESSAGENET_PASSWORD=<your MessageNet SIP password>
```

The `MESSAGENET_USER` value is the part **before** `@` in `sip:NNNNNN@sip.messagenet.it`.

### Step 2: Start the asterisk service

```bash
docker compose --profile messagenet up -d asterisk
```

Without the `messagenet` profile the asterisk container is not created, so existing dev setups are unaffected.

### Step 3: Restart the api container

The Stasis listener boots from the FastAPI lifespan, so the api container needs to come up *after* the env vars are set:

```bash
docker compose up -d --force-recreate api
```

You should see `[MessageNet] SIP gateway backend installed: asterisk-ari` and `[MessageNet/Stasis] Connected to ARI events for app=dograh-messagenet` in the api logs.

### Step 4: Save a MessageNet telephony configuration in the UI

Open `/telephony-configurations`, click **Add configuration**, pick **MessageNet**, and enter the same `sip_uri` / `username` / `password` you put into `.env`. The provider configuration and the Asterisk PJSIP trunk are two separate stores — Dograh uses the UI row to authorize and tag outbound calls, while Asterisk uses its own config to actually speak SIP.

### Step 5: Place a test call

From a workflow's **Test Call** action, dial an E.164 number. In the logs you should see, in order:

1. `[MessageNet] Initiating outbound call to +…`
2. `[ARI Channel created: …]` (from the AsteriskARIGateway originate)
3. `[MessageNet/Stasis] Outbound StasisStart channel=… workflow_run_id=…`
4. `[MessageNet/Stasis] Bridge … live: trunk=… ext=…`
5. The pipecat pipeline starting on the externalMedia WebSocket leg

### Audio bridge via AudioSocket

Audio between Asterisk and the Dograh pipecat pipeline runs over **AudioSocket** (TCP), not over chan_websocket. The chan_websocket externalMedia transport is broken in `andrius/asterisk:21`, so the bundled stack uses chan_audiosocket instead.

How it works:

1. `MessagenetStasisListener._create_external_media` generates a UUID, pre-registers it with the deployment-level `AudioSocketServer` (api side, port 9092), then issues `POST /channels/externalMedia` with `transport=tcp`, `encapsulation=audiosocket`, `external_host=api:9092`, `data=<uuid>`, `format=slin`.
2. Asterisk opens a TCP connection to `api:9092` and sends a first frame `type=0x01` (UUID) containing the 16-byte UUID.
3. `AudioSocketServer` matches the UUID to the workflow run and opens a loopback WebSocket to its own `/api/v1/telephony/ws/ari?workflow_id=…&user_id=…&workflow_run_id=…` endpoint.
4. The bridge transcodes audio bidirectionally — AudioSocket carries PCM16 (slin), the existing `AsteriskFrameSerializer` expects µ-law on the WebSocket side, so the bridge runs `audioop.lin2ulaw` / `audioop.ulaw2lin`.

Env knobs (optional; sensible defaults work for the bundled stack):

| Var | Default | Purpose |
|---|---|---|
| `MESSAGENET_AUDIOSOCKET_PORT` | `9092` | TCP port the AudioSocket server binds. Same port is used as `external_host` toward Asterisk. |
| `MESSAGENET_AUDIOSOCKET_HOST` | `0.0.0.0` | Bind address. |
| `MESSAGENET_AUDIOSOCKET_TARGET_HOST` | `api` | Hostname Asterisk uses to reach the AudioSocket server. Default matches the docker service name on `root_app-network`. |
| `DOGRAH_WS_HOST` | `localhost:8000` | Host:port the loopback bridge connects to for `/ws/ari`. |

The TCP port is internal to the docker network — no host port mapping is needed.

### Inbound calls

When MessageNet sends an INVITE to a DID associated with this trunk:

1. Asterisk's `dograh-inbound` dialplan answers and hands off to the `dograh-messagenet` Stasis app with `direction=inbound&to=<exten>&from=<callerid>` appArgs.
2. `MessagenetStasisListener._on_inbound_stasis_start` looks up the called number via `db_client.find_phone_number_for_provider_address("messagenet", to)` — this is org-agnostic (unlike the org-scoped `find_active_phone_number_for_inbound`) because the listener is deployment-level. The query joins `telephony_phone_numbers` with `telephony_configurations` filtered to `provider='messagenet'` and `is_active=true`.
3. The matched phone number must have `inbound_workflow_id` set; the workflow is loaded scoped to its owning org, quota is checked, and a `workflow_run` is created with `mode=messagenet`, `call_type=INBOUND`, and `initial_context.{caller_number, called_number, direction, provider, telephony_configuration_id}`.
4. From there it joins the same externalMedia + bridge sequence as outbound — Asterisk's already-Up trunk channel gets bridged with an AudioSocket leg, the loopback WebSocket connects to `/ws/ari`, and the pipeline runs.

To enable inbound routing for a MessageNet DID, register it in the UI under the MessageNet telephony configuration and assign it an `inbound_workflow_id`. If the assignment is missing the listener logs `phone number row id=… has no inbound_workflow_id assigned — hanging up` and rejects the call cleanly.

### What's not wired yet

- **Call transfer** is still phase 2 on the MessageNet provider itself (`supports_transfers()` returns `False`).

## Limitations (Phase 1)

- **No REST call-control API** — MessageNet is SIP-only. All control plane and media-plane operations route through your SIP gateway.
- **SIP/media gateway is required** — without one, outbound calls fail with HTTP 503 and inbound calls won't reach Dograh.
- **Cost retrieval is not implemented** — MessageNet does not expose a per-call cost API. CDR reconciliation is a deployment-level concern.
- **Call transfer is phase 2** — `transfer_call` raises `NotImplementedError`. Implement transfers using SIP re-INVITE / REFER on the gateway side once your deployment needs them.
- **Inbound matching is by called number** — no account-id matching across trunks.

## Troubleshooting

| Symptom | Likely cause | Action |
|---------|--------------|--------|
| `HTTP 503 — MessageNet SIP gateway is not configured` | Default stub gateway is still active | Wire a real `MessagenetSipGatewayClient` for this deployment |
| `HTTP 400 — MessageNet provider is not properly configured` | `sip_uri` or `password` missing/blank on the saved config | Re-open the configuration in Dograh and confirm both fields |
| Outbound call placed but audio never starts | Gateway answered SIP but the WebSocket audio leg failed | Check the gateway's external-media configuration; mismatch in sample rate (`8000 Hz`) or codec (`PCMU`/`PCMA`) is the usual culprit |
| Inbound call rings on MessageNet side but doesn't reach Dograh | Gateway dialplan isn't routing the dialled number into the Dograh WebSocket bridge | Verify the dialplan extension for the inbound DID points at your Dograh-facing endpoint |
| `[MessageNet/Stasis] Inbound call to <DID> ... no active phone number registered in any messagenet config` | Inbound DID isn't registered (or `is_active=false`) on any messagenet `telephony_configurations` row | Add the DID under the trunk's configuration in the UI and assign it an `inbound_workflow_id` |
| `[MessageNet/Stasis] phone number row id=N has no inbound_workflow_id assigned` | DID is registered but no workflow handles inbound | Edit the DID row in the UI and pick an `inbound_workflow_id` |
| Asterisk logs show `Outbound registration to sip.messagenet.it failed` | Wrong `MESSAGENET_USER` / `MESSAGENET_PASSWORD` in `.env`, or the asterisk container started before they were set | `docker compose --profile messagenet restart asterisk` after correcting `.env` |
| Carrier returns `SIP/2.0 500 ... server error (6/TM)` on outbound INVITE; SDP body has no `m=audio` line | `res_pjsip_sdp_rtp.so` (or its RTP-engine deps `res_rtp_asterisk.so`, `res_rtp_multicast.so`) isn't loaded — chan_pjsip sends a header-only SDP that strict carriers reject | Confirm the modules are loaded with `asterisk -rx 'module show like rtp'`; the bundled `asterisk/modules.conf` already loads them |
| `[MessageNet/Stasis] ARI POST /channels/externalMedia failed: HTTP 500` and the outbound trunk is hung up right after StasisStart | chan_websocket externalMedia is broken in `andrius/asterisk:21` even though sorcery has the entry. | Resolved in this repo by switching to **AudioSocket transport** (TCP) — see [Audio bridge](#audio-bridge-via-audiosocket) below. The chan_websocket path is no longer used. |
